# ML-1 fit population — the fit now reads a multi-era window (and it does not buy a promotion)

**Card:** `ml1-fit-population-gaps` (Done) · approvals id `apr-ml1-fit-population-gaps` · **Lane B**
**Date:** 2026-11-12 · **Status:** instrument repaired, artifact regenerated, **nothing promoted** — no RuleSet, threshold, sizing, or live lane moved.

---

## 1. Key insight

The card asked one question in two halves: does the fit population carry the purge key, and is the
train window a single era? By the time this run started, both halves were **visible** but only one was
**fixed**.

- **Claim (1) — terminal stamp / purge.** Already fixed (9468900 → `1048314`). Verified again today on
  the live file: `training_data.csv` carries `terminal_at` at column 14 with **5,841/5,841 populated**,
  **0 rows** with a terminal stamp earlier than the decision, and the frozen time split purges **487**
  label-tails. The purge runs on the file the model is fitted on. Do not re-fix.
- **Claim (2) — single-era train window.** The *gate* could cut on regime (`ml1-gate-read.ts --split era`,
  shipped 10-28) and the *verdict* printed the era mix (shipped 10-28). The **fit harness could not**:
  `ml1-fit-candidate.ts` called `readArms` with no split argument, so every candidate in
  `data/ml1-fit-candidate.json` was fitted on the frozen time window — **train 2,300 rows, 100%
  pre-kelly-v1-48, `trainEraCount: 1`** — with no second window in the artifact to answer it. That is
  the half this run closes: one config object in the fit harness, plus an artifact regeneration.

**The measured answer: adding a second training era does not recover the forward-era gap.** On the
multi-era window (pre-kelly + kelly-window) the fitted family still lands at or below price on the held-out
regime, and the in-sample→held-out gap is unchanged. That was the one thing the 10-28 era read could not
say, because its fitted arms were still trained on regime 1 only, i.e. they priced the *cost of
extrapolation*, not the *value of more eras*. The value is zero-to-negative.

## 2. What changed

| File | Change |
|---|---|
| `src/lib/ml1-read.ts` | `FIT_POPULATIONS` + `fitPopulations()` + `parseFitSplitMode()` — the fit populations as one config object. The published time population keeps its **original artifact label**; the era population is a second, additional entry. |
| `scripts/ml1-fit-candidate.ts` | Reads `--split time|era|both`, **defaults to `both`**. Loops the configured populations, prints the train era mix per population, records `fitSplitMode` / `fitPopulations` / `fitPopulationSummary` in the artifact. |
| `tests/ml1-era-read.test.ts` | 3 new tests: default is both; unknown `--split` throws instead of falling back to one era; the era population really does fit on **2 eras** with a clean regime cut. |
| `data/ml1-fit-candidate.json` | Regenerated by `npx tsx scripts/ml1-fit-candidate.ts` (4m44s). |

Three guarantees, each of which can fail:

1. **A single-era train window on the era cut FAILS the run** — it does not print a clean-looking read.
2. **An unknown `--split` value throws** — a typo cannot silently restore the defect.
3. **The bar population stays pinned to the frozen time split.** `decision-dataset.csv` (built
   2026-09-13) holds zero exposure-v58plus rows; an era cut there is an empty test set by construction,
   so the split throws. Same pin as the gate CLI.

`BOUNDARY`, `BAR`, and the frozen time split are untouched.

## 4. Reality checks

- **It is still one regime draw.** n=1,236 legs on one held-out era cannot separate "regime 3 is harder"
  from "regime 3 was unlucky" — the same caveat the 10-28 read recorded. The direction is consistent
  across three independent reads (static arms 10-28, fitted arms 10-11 on regime-1 train, fitted arms
  today on eras 1-2 train), which is why the conclusion is stated as "no value detected", not "proven zero".
- **Price's own decay is the driver.** Price falls 0.7592 in-era → 0.6849 on the held-out regime. A model
  cannot out-rank a comparator whose discrimination is itself decaying.
- **Adding an era grew the train window 1.7×** (2,300 → 3,927 rows) and the overfit gap did not shrink;
  C3's in-sample 0.7341 still lands at 0.6676.
- **This is an instrument, not a model.** Nothing in the live path reads `data/ml1-fit-candidate.json`.
